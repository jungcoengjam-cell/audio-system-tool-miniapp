# 全项目代码与性能审查（2026-09-05）

## 范围与结论

本轮按 GPT-6 Astra 定位、设计与独立复审，GPT-5.6 Luna 实施并返工的流程进行。检查覆盖 16 个主包页面、2 个分包页面、共享模板/样式、八个计算模块、产品查询、项目记录、图片生成、生命周期与发布检查。

结论：有局部维护债和可复现的边界错误，但没有需要推倒重写的依据。主要风险集中于跨页面状态同步、异步回调、读取失败后的写入，以及将完整结果重复传给视图。已有的计算模块分离、产品资料懒加载、分页和性能采样可以继续保留。

本轮没有改产品资料、物理参数、DMX 域容量或通道编址规则，也没有新增依赖、改版本号或上传正式版。LED 搜索算法有实质修正：落实原有“安装得下、比例偏差在 5% 内尽量最大”的规则，而非修改推荐标准。

## 已修复的问题

| 位置 | 原问题 | 修复与验证重点 |
| --- | --- | --- |
| 项目记录对比 | 选满两条后，再点击已选记录也被当作第三条拒绝 | 先判断取消选择；保留最多两条和同模块限制 |
| 项目进入会议室计算 | 旧缓存覆盖新设置，重置后可能带回旧偏好 | 合并项目尺寸前读取当前偏好；验证更新、重置和失败重试 |
| 项目/记录存储 | 读取异常可能被当作空数据，迁移或保存时覆盖已有记录 | 迁移读取不齐不写；一次修改中读取失败则拒绝写入；不缓存失败兜底值，后续操作可重试 |
| 通用结果图片 | 中途离页取消后，按钮可能一直处于生成状态；旧失败回调弹提示 | 取消时恢复生成状态；旧成功/失败回调不能结束或覆盖新请求 |
| 灯具位置图 | 横屏标记变化返回竖屏后未重读，后续操作可能覆盖标记 | 返回时同步同方案进度，清理旧选中与旧图缓存 |
| 灯位配置 | 改变灯杆排数或侧光配置后，配置行仍为旧数量 | 配置定义、计数和视图行同步；展开时刷新 |
| 位置图缩放 | 平移边界按中心原点计算，与实际左上原点不一致，右下区域不可达 | 平移限制改为负溢出量至零；验证 1、2、2.5 倍与触点逆变换 |
| 位置图导出 | 页面卸载后，迟到回调仍更新页面或打开预览 | 生成令牌与页面存活检查；覆盖 nextTick 前卸载和导出后迟到回调 |
| 自定义灯具通道 | 从库内切到自定义后仍关联原产品的已核对通道 | 旧型号仅保留为编辑缓存；实际自定义结果不带旧型号；切回库内仍能恢复 |
| LED 最大尺寸 | 候选列只取最接近目标比例的值，漏掉容差内更大的屏 | 补全 5% 上界候选，解析宽度受限尾部的可行行数 |
| LED 异常输入 | 空值/非有限预留值被当作零；超大输入存在计数不可靠或高耗时风险 | 明确校验预留、包边、毫米换算和安全整数范围 |

LED 复现例：8.321 m × 4.321 m 墙面，320 × 160 mm 模组，16:9，预留与包边均为零。旧结果为 24 列 × 27 行、648 块；修正为 25 列 × 27 行、675 块，仍在既有 5% 比例容差内且可安装。

## 性能结果

测试使用真实生产页面、真实 DMX 地址计算及项目记录 API；仅将微信存储和 UI API 替换为内存测试环境。每条方案包含 500 台灯具，未读取或修改用户实际存储。

| 场景 | 修改前单次视图更新 | 修改后 | 减少 |
| --- | ---: | ---: | ---: |
| 35 条记录的项目页 | 1,302,852 B | 12,240 B | 99.1% |
| 70 条记录的项目页 | 2,606,462 B | 22,635 B | 99.1% |
| 70 条记录的收藏列表 | 1,303,899 B | 17,821 B | 98.6% |

完整地址表、恢复参数和对比源数据留在逻辑层，视图只接收标题、摘要、状态等必要字段。完整复制文本另做断言，未通过截断原始记录来减小载荷。

LED 搜索减少逐行扫描。在本机 Node 压力对照中，500 m × 500 m 输入连续计算 500 次，旧实现约 62.75 ms，新实现约 2.23 ms。这只是算法压力样本，不代表真机首屏或整机帧率提升比例。

## 验证方式

- 发布入口：`node tests/release-check.js`。新增 runtime、DMX、LED 三个专项回归作为独立子进程执行，任一失败即阻止总检查通过。
- LED：项目内固化 15,000 组独立全行列穷举对照；Astra 另外完成 42,000 组对照，均一致。
- 存储：注入 schema、项目、记录、偏好读取失败，检查原数据保留、失败操作不写入、后续重试正常。
- 图片：检查取消、新旧请求交错、卸载和迟到成功/失败回调。
- 性能：35/70 条真实记录的视图载荷固定预算，测试不依赖个人临时路径。
- 原生编译：微信 WCC 检查 19 个 WXML，WCSC 检查 20 个 WXSS，均通过。

测试与审查文档已被现有打包配置排除，不进入小程序正式包。未提高包体预算来绕过检查。

最终统一发布检查通过。按现有打包排除规则计算的源码包为 1407.9 KiB，内部预算 1408.0 KiB；主包 JS 647.7 KiB、DMX 分包 JS 235.4 KiB、WXSS 211.2 KiB、WXML 188.1 KiB。数据保护和算法校验增加了少量代码，本轮优化目标主要是运行时效率与正确性，不是让总包体积减少。

修改的生产文件：`utils/records.js`、`utils/result-report-controller.js`、`utils/led-screen.js`、`pages/records/project.js`、`pages/projects/projects.js`、`pages/dmx-layout/page-factory.js`、`pages/dmx-address/dmx-address.js`。

测试修改：`tests/release-check.js`，以及新增的三个 `audit-*-regression.js` 和 `tests/helpers/record-view-payload.js`。原始源码备份位于本地工作区 `tmp/astra-global-audit/before`。

## 维护债与下一步

1. 灯具位置图页面控制器约 1,600 行，手势、排布、存储、导出职责较集中。适合在后续独立任务中按职责小步拆分，先保留现有行为测试，避免一次性重构交互。
2. 主发布测试约 6,700 行，部分断言依赖源码文本。今后新增行为测试应保持独立模块；此次已按这一方式接入三组回归。
3. 部分源样式为长行压缩格式，修改和评审成本较高。建议之后单独做可读性整理与等价验证，不在本次缺陷修复中混入全局格式化。
4. 现有内部包体预算余量很小；后续新增功能前应先处理对应模块的体积冗余。该数字是项目内部预算，不是微信平台上传上限。

这些是后续维护建议，不代表本轮已完成整体架构重写。

## 真机验收边界

本轮完成代码、自动化行为和原生模板编译验证，未替代手机端手势、系统主题及微信分享实测。建议正式发布前重点检查：

1. 位置图放大后四角均可到达，拖动落杆位置正确；横屏标记/取消后返回竖屏保持一致。
2. 生成图片时退出，再进入能重新生成；没有旧图残留、旧提示或按钮锁定。
3. 项目两条记录对比可取消；完整地址表复制、记录恢复和报告图片内容正常。
4. LED 示例和常用带包边输入正确；浅色/深色下关键页面仍正常显示。

全项目审查不能保证不存在任何未知问题；本报告区分了已复现修复、自动化验证和仍需真机确认的范围。
